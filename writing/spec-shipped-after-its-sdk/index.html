The MCP spec shipped one day after its SDK — and the SDK still can't speak it

If you run a Model Context Protocol server written in TypeScript, a twelve-month clock started on 28 July 2026. The natural reaction is to plan a migration sprint. Check your tooling first: as of today it cannot be done.

What the July release changed

The 2026-07-28 specification is not a routine revision. It turns the core protocol inside out, in the words of the release itself:

MCP is transforming from a bidirectional stateful protocol into a request/response stateless protocol.

Concretely: the initialize/initialized exchange is retired, and so is the Mcp-Session-Id header along with the protocol-level session it carried. What used to be negotiated once at connection time now travels in _meta on every request. The legacy HTTP+SSE transport is deprecated with a year-long off-ramp, and Dynamic Client Registration gives way to client metadata documents.

For a server author the practical consequence is the session. If you kept anything per session — a cursor, a cart, a last-read window, a user binding — that hiding place is going away. The specification's own migration advice is to make the state visible instead:

Servers can mint an explicit handle (a basket_id, a browser_id) from a tool and have the model pass it back as an ordinary argument on later calls.

Then we went to migrate, and stopped

Before touching our own production server we did the cheapest possible check: what protocol versions does the installed SDK actually support? The answer is in the package itself.

Measured 2026-08-10

$ npm view @modelcontextprotocol/sdk dist-tags
{ "latest": "1.30.0" }

# publish time of that version
2026-07-27T17:56:01.640Z

# node_modules/@modelcontextprotocol/sdk/dist/esm/types.js
LATEST_PROTOCOL_VERSION = '2025-11-25'
DEFAULT_NEGOTIATED_PROTOCOL_VERSION = '2025-03-26'
SUPPORTED_PROTOCOL_VERSIONS = ['2025-11-25','2025-06-18','2025-03-26',
                               '2024-11-05','2024-10-07']

No 2026-* version appears anywhere in that list. There is no beta or next dist-tag to opt into. Across 79 published versions the only major branches are 0 and 1.

Note the two dates next to each other. The specification was released on 28 July. The most recent SDK was published on 27 July — the day before — and has not been updated since. The tool that would implement the new protocol predates the protocol.

So the honest status is not "we are behind on the migration". It is "the migration has not started anywhere in the TypeScript ecosystem, because it cannot". If a vendor offers to migrate your TypeScript MCP server to the July specification today, ask them which SDK version they intend to use.

What to do with a twelve-month clock and no tooling

Waiting is the correct decision, but idle waiting wastes the runway. Three things are worth doing now, and all of them are cheap:

  • Watch one thing, not a newsletter. The trigger is a 2.x release or a beta channel appearing on the SDK. That is a single command (npm view @modelcontextprotocol/sdk dist-tags) run every couple of weeks.
  • Inventory what genuinely depends on the session — separately for your application logic and for your transport plumbing. These usually turn out to be very different sizes.
  • Decide the handle design before you need it. If state must survive, which identifier does a tool return, and what stops one user's handle from being replayed by another? That question is easier answered calmly than during a migration.

The part that surprised us

When we ran that inventory on our own production server, we had already done half the migration without meaning to. Our application state — the practice journal, the last window of source text a user had read — was moved off the session and onto the user back in early August, while fixing something else entirely: we had discovered that one host opens a fresh MCP session on nearly every tool call, so per-session memory was already unreliable in practice. Separately, we had taught the server to serve any request that arrives without a live session, because a view's callback would otherwise die against a session id the host had cached.

Both changes were bug fixes for host behaviour. Both turn out to be exactly what the stateless specification asks for. What remains session-bound on our side is only transport plumbing — the map from session id to transport instance, and a binding to the token owner that becomes redundant once every request is authorised on its own.

There is a general lesson in that. The hosts are ahead of the specification in the ways they break you. If you have been fixing real host behaviour rather than coding to the document, some of your migration may already be behind you.
