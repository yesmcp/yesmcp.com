What the host doesn't deliver

The specification tells you a field exists. It cannot tell you that a particular host puts it in front of the model. Those are two different facts, and only the first one is written down. Everything below is the second kind, learned the expensive way.

A caveat before the list: these were measured against one vendor's host — Claude, in its web, mobile and desktop forms. We have not tested the others, so we do not claim anything about them. That restraint is the point of the article.

1. The instructions field does not arrive

An MCP server can declare instructions, and it reads like the natural home for "how this server should be used". We put a unique marker string in it — the sort of token that cannot be guessed — and asked the model whether it could see it. It could not, in any form of the question.

Consequence: any behaviour you place there is decoration. Ours moved to tool descriptions, which do arrive — and, for a while, into tool results, which turned out to be its own kind of mistake.

2. A tool's description is unreachable until the tool is loaded

Hosts do not always hand the model every tool at once; some are deferred and fetched on demand. A deferred tool's description therefore cannot tell the model when to use that tool — the model has to already be reaching for it to read the instruction.

We learned this from an empty journal. Our writing tool carried a clear description saying "call me at the end of every session". The model never called it, so it never read the description saying to call it. The fix that worked was to put the obligation in the response of a neighbouring tool that was loaded — and, separately, to write the first phrase of the description in English, because the host's tool search is queried in English.

3. A new session on nearly every call

We built the server assuming a conversation maps to a session. It does not. In production logs, a single conversation opens a fresh MCP session repeatedly — a distinct session id for almost every tool call.

From one 20-minute session, production logs

Twelve tool calls, roughly 52 HTTP requests, and a different session id on each call. Anything stored in a per-session variable is gone by the next call.

Two consequences worth internalising. First, keep state per user, not per session — ours moved to the user early, and that is also what the July 2026 specification now asks of everyone. Second, a view calling back into your server may present a session id the host has cached and your server has long since retired; answering that with a 404 breaks the view. Serving any well-authorised request without requiring a live session fixed it for us.

4. The tool list is re-sent before every single call

This one is a cost, not a bug, and it never appears in an estimate unless you look.

Measured in production

Before each tool call the host re-fetches the tool list: 5698 bytes, every time. Over a twelve-call session that is roughly 68 KB of pure repetition, alongside the actual work — which in our case was 0–4 ms per call for everything except a corpus search at 470 ms.

If you are sizing a deployment, the traffic model is dominated by protocol overhead rather than by your payloads. Every tool you add is paid for on every call, by every user, forever — which is a good argument for a small, well-chosen tool set independent of any prompt-quality concern.

The method: marker tests

All four findings came from the same cheap technique, and it is the transferable part of this article. When you need to know whether a channel reaches the model, put a unique nonsense string into it — something that exists nowhere else — and ask the receiver whether it sees it. The answer is binary and cannot be faked by a plausible-sounding model. Formulate the expectation before running it, or any outcome will look like confirmation afterwards.

The discipline behind it is simpler still: a specification, a JSDoc comment, a README, and a model's own recollection are all hypotheses about behaviour. They become facts after one decisive test on the real system. That test costs minutes. Finding out from a client costs the engagement.
